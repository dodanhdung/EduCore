# R9.4 pilot OTP delivery decision — PROPOSED, owner security review required

**Decision state:** `OWNER_DECISION_REQUIRED`. The checked-in `recovery-worker-main.ts` calls `localWorkerFromEnv`, which rejects `NODE_ENV=production` with `PRODUCTION_OTP_WORKER_NOT_APPROVED`. Its `LocalSmtpRecoveryDelivery` accepts only loopback SMTP, `.invalid` sender and recipient, and an unencrypted local socket. The current synthetic smoke proves the queue and restricted worker path locally; it does not send real email. Do not remove or bypass this guard, use development cookies for real users, or claim onboarding/recovery is ready.

`config.ts` can compose `SmtpOtpDelivery` for direct **activation** OTP delivery with TLS, but `AuthService.requestOtp(PASSWORD_RESET)` enqueues an encrypted recovery envelope and does not use that direct adapter. Enabling `R4_OTP_MODE=smtp` alone therefore does **not** close production password recovery. Activation's best-effort delivery/restart behavior also needs target-host testing and an operator resend procedure.

## Minimal recommended option

Approve a **separate production delivery adapter and entry point** in a later, reviewed security slice. Reuse the existing `RecoveryWorker` claim/check/finish/sweep state machine and `educore_r4_otp_delivery` database role; leave the local-only adapter and production guard intact. The new adapter must require an allowlisted approved SMTP host, authenticated TLS (implicit TLS or validated STARTTLS with downgrade refusal), certificate validation, sender-domain ownership and bounded connection/response timeouts. It must return the existing `ACCEPTED`/`TRANSIENT`/`PERMANENT`/`UNKNOWN` outcomes without logging recipient, OTP, message, credentials or envelope. Treat SMTP acceptance as acceptance by transport, not proof of inbox delivery. No arbitrary outbound host or plaintext fallback.

The operator provisions a separate restricted LOGIN inheriting only `educore_r4_otp_delivery`. `RecoveryWorker.assertRuntime()` must pass and the login must have no AUTH/API/business-worker/operator membership, public `CREATE`, table `SELECT` on delivery envelopes, or ability to request OTPs. API and worker receive only their required recovery keys via a protected secret store; no key in Web assets, Git, command arguments, logs or review ZIP. The API holds the active AES-256-GCM encryption key; the worker holds a key map for decrypting pending envelopes. The existing AAD binds OTP ID, purpose and key ID. Rotate by distributing the new key to worker first, then making it active on API, while retaining the former key until all old envelopes expire or reach terminal state; verify drain before retiring and destroying it. Back up keys separately from database snapshots under named custody, access logging and a tested recovery procedure. An unavailable key must fail delivery safely and alert an operator, not expose or reissue an OTP silently.

The existing SQL delivery queue retries transient/unknown outcomes with 1/3/5 minute delay, at most four attempts, subject to the 15 minute OTP window; permanent failures terminate. Leases/fencing prevent stale workers from finalizing a newer claim; terminal rows clear ciphertext and are swept after seven days. Operators monitor READY/RETRY_WAIT age, FAILED/EXPIRED counts, `SMTP_TIMEOUT_UNKNOWN`, key errors and worker heartbeat without collecting OTPs or recipient addresses. On transport outage, pause invitations/recovery claims as needed, fix the dependency, and have the user request a fresh OTP after expiry. Do not disclose whether an address exists. The public request remains generic 202 for known/unknown eligible cases within the current throttle; reset stays atomic, single use and 15 minute expiry, and revokes old sessions. Preserve current response-shape, rate-limit and official timing assertions.

Before real users, test on an isolated pilot-like host with synthetic owned mailboxes and reviewed HTTPS/secure-cookie configuration: restricted-role startup, TLS certificate failure, SMTP 4xx/5xx and timeout, queue retry/final state, key rotation and missing-key alert, generic known/unknown request shape, throttle, expiry, one-use reset and old-session revocation. Then do a controlled owner-approved real mailbox delivery and measure acceptance versus actual receipt without storing the OTP in evidence. Record a failed-delivery escalation contact, manual identity-verification procedure and stop rule. This proposal does not authorize implementation, external SMTP use or deployment.

## Options and tradeoffs

| Option | Engineering/operating cost | Risk and decision |
| --- | --- | --- |
| Separate secure SMTP adapter/worker using existing queue (**recommended**) | Small bounded code slice plus SMTP account, secret custody, monitoring and test host | Keeps current queue/ACL and local guard. Needs owner-approved security design, tests and real delivery before invitations. |
| Approved OTP-only delivery provider transport behind the same worker port | Similar adapter work plus provider contract and outage procedure | Provider dependence and data handling need review; no broader business email permission follows. |
| Development-mode local worker or disabled recovery | Little immediate code | **Unacceptable for real users:** local adapter cannot deliver real OTP; development cookies/security mode and incomplete recovery violate UC-03. Synthetic demonstration only. |

**Current activation classification:** real-user pilot `BLOCKED` on production-compatible recovery until a separate implementation and operational verification are approved. Synthetic MVP demonstration may proceed. Independently, the official OTP timing equivalence case remains FAIL and `PILOT_SECURITY_RISK_ACCEPTANCE_REQUIRED`; owner approval of D1 diagnostic does not accept that risk.

## Questions and hypotheses

The external observable is elapsed time from initiating an HTTP POST to receipt of complete response, plus status, body, relevant headers and 429 behavior. Primary AUC is `P(T_known>T_unknown)+0.5 P(tie)`, with labels assigned only by synthetic fixture membership. Median and p95 differences (known minus unknown) guard against distribution changes obscured by AUC. Repeat-measurement attack feasibility is assessed against the current IP budget and one-minute known-address issuance suppression, not merely against an unconstrained single-request AUC.

Two questions must be kept separate:

1. **Difference detection:** H0 AUC=.5 against two-sided H1 AUC≠.5, with tail, shape and rate-limit differences inspected separately. Non-rejection does not establish safety.
2. **Equivalence:** H0 AUC≤.45 or AUC≥.55 against H1 .45<AUC<.55, alongside the existing median/p95 limits and response-shape equality. AUC outside the band can be exploited in either orientation if an attacker has adequate observations. The [.45,.55] band is the **current official contract**, not an empirically validated attacker-risk threshold. Any alternative is `PROPOSED — OWNER APPROVAL REQUIRED`.

At AUC .55 or .45, a single independent known/unknown pair is ordered correctly in the favorable direction 55% of the time (ties counted half), a five percentage-point advantage over chance. Repeated samples can amplify ranking accuracy, but pairwise AUC is not the accuracy of a particular limited-budget attacker classifier. **PROPOSED — OWNER APPROVAL REQUIRED:** treat a held-out attacker classifier with at least 60% balanced accuracy and false-positive rate at most 10%, using no more than 10 accepted requests per candidate from one IP in one one-minute window, as a practically relevant timing signal needing mitigation review. A distinct distributed-IP scenario is reported separately. This is a review trigger, **not** a replacement acceptance margin or evidence that the current system meets it. The exact practical threshold remains uncertain without deployment-like noise, candidate probe budget and attack simulation. For sensitivity, report true AUC .50, .52 and .55; do not adopt .52 or .55 as a new acceptance margin without owner decision. Inspect p95 and above-floor tails even if median/AUC pass.

## Randomization, warm-up and timing

- D1 fixed integer seed `0xD01C04`; C1 `0xD01C05`; C2 `0xD01C06`. Use the same 32-bit LCG recurrence as the official test, document generator/version, generate balanced eight-position orders in complementary pairs, then Fisher–Yates shuffle the block order. Seeds and generated counts are written before execution; changing a seed after seeing data invalidates that run. Fixture email token is independently random and redacted from published evidence.
- Warm up 100 requests alternating known/unknown, with four-wide waves, unique synthetic addresses and fresh block IPs; drain eligible recovery deliveries before timing starts. Record warm-up duration/worker outcome, exclude only these planned requests. D1 cold-connection cells explicitly start after a newly initialized restricted client; warm cells reuse it. C1 uses warmed connections only. No ad-hoc additional warm-up.
- Measure from immediately before the HTTP client starts the POST through complete receipt of status, headers and body using `process.hrtime.bigint`. Before requests, measure 10,000 consecutive clock reads and a label-blind null HTTP path; report clock quantization, timing overhead and p95 drift across beginning/end control batches. A clock resolution worse than 0.1 ms or null-path drift above 1 ms makes sub-millisecond label effects **INCONCLUSIVE**; retain all observations. Record server controller-entry, throttle, readiness, service-call start/end, SQL span, pool wait where instrumentable, response deadline, final response, worker counters and event-loop delay only in D1 test-local trace. Quantify `serviceEnd - responseFloorDeadline` and `responseEnd - responseFloorDeadline`; count and stratify overruns for each label. Do not infer a 100 ms floor from client elapsed time alone, since client overhead adds latency.
- Set a 2-second per-request response timeout for D1/C1. Timeouts, 429s, 503s, malformed shapes, missing data and instrumentation failures are **failures/observable outcomes**, never dropped as outliers. The existing official test's timeout behavior remains unchanged. Do not discard slow samples, reset a condition, or stop early for a favorable CI. Abort the *entire run* only for failed admission, process crash, lost DB connection, worker harness failure or environment drift; report the partial data and label the run invalid. Retry only on a new cluster under a documented predeclared infrastructure-failure rule; never retry a statistical FAIL.
- Keep the original synthetic per-block IP rotation for comparability. Separately run **54 D1 attacker-budget requests**: with one test IP, 10 requests followed by one expected 429, wait for the anchored one-minute window to expire, then 10 more plus one expected 429; use matched known/unknown addresses including a repeated known candidate. With four distinct test IPs, send eight requests each (32 total) and report their accepted/429 counts. This probes the current IP budget; it does not establish global attacker budget. Do not use spoofable forwarding headers outside the local trusted-proxy fixture. Record exact proxy/edge behavior and internet-like network conditions only if actually measured; loopback remains loopback.

## Analysis and decisions fixed in advance

Analyze each condition separately. Publish counts, shape equality, AUC with tie handling, known/unknown median and p95, percentile intervals, slot and time-block summaries, above-floor fractions, and labeled internal service summaries. For D1, retain the official pooled estimator and 10,000 whole-block resamples, using its planned 40 blocks; D1 is descriptive and cannot be directly compared on CI width with the 100-block historical runs. For C1/C2's **proposed** larger design, resample whole eight-request blocks 10,000 times with fixed resample seed `runSeed + conditionIndex`, and compute percentile 95% CIs. Check autocorrelation and drift on the first half/second half and per-slot estimates before interpreting coverage; do not revise the primary estimator after seeing results. A distinct slot-stratified or moving-block estimator, if adopted, needs a separately frozen version and owner approval. The power estimates in the companion document are i.i.d. normal approximations with an explicit design-effect sensitivity, not a guarantee that this bootstrap is calibrated.

**For the existing contract:** every original condition must have identical public response shape, entire 95% AUC CI inside [.45,.55], entire median-difference CI inside its current ±max(10 ms, 5% pooled median), and entire p95-difference CI inside ±max(25 ms, 10% pooled p95). Any failed/inconclusive condition keeps the gate PARTIAL. Equality at the interval boundary follows the existing `>=`/`<=` code. No optional stopping, favorable-run selection or after-the-fact exclusion.

**For owner review:** evaluate the proposed practical classifier trigger only on held-out synthetic candidates, with threshold fixed from calibration data and both class errors reported. A validated external classifier under a feasible IP/request budget, stable response-shape difference, or repeatable above-floor label asymmetry triggers a production/security review even if an aggregate AUC interval falls inside the band. If test assumptions or bootstrap coverage fail, report **INCONCLUSIVE** and repair the methodology only by a new preregistered owner-approved version. C1, C2 and D1 must all be reported, including failures. Do not combine runs as if they were independent requests without modeling run/environment effects. A final release decision also needs deployment-like edge and load evidence; loopback equivalence is not sufficient proof of internet-facing safety.

## Threat model and decision target

An **external unauthenticated attacker** can submit candidate email addresses and observe status, body, headers, elapsed HTTP time and 429 behavior. A single IP is limited by the current OTP throttle to **10 attempts in a one-minute window anchored at the first attempt** for the combined `otp` operation. The key is an HMAC of IP and operation; this is an IP control, not a demonstrated global or per-address budget. An attacker with multiple egress IPs may obtain more observations. The SQL also suppresses repeated eligible known-account issuance within one minute, so repeated requests against one candidate need not have the same internal path as first requests. A realistic attack might compare many candidates and controls, wait between probes, or distribute across IPs. Proxy trust and deployment edge behavior must be verified before treating a supplied forwarding header as attacker-controlled or protected. No internet-facing latency, jitter, concurrency, IP-distribution limit, or actual enumeration accuracy has been measured.

An **internal diagnostic observer** can instrument Node, DB calls, pool waits and worker state, and can label synthetic known/unknown accounts. That observer has privileges unavailable to the attacker. Internal service duration helps locate causes but cannot alone establish an exploitable HTTP signal. The decision target is the full externally visible response and timing distribution, including tails, under the allowed attacker request budget. Loopback Supertest with trusted loopback proxy is a useful controlled experiment, not a production network model.

The route validates email, registers a common 100 ms timer, calls IP throttle and recovery readiness, then awaits `AuthService.requestOtp`. The known-account SQL selects/locks an active user, may invalidate prior OTPs and insert hashed OTP/encrypted delivery; unknown returns false. The worker uses a distinct restricted connection and sends later. Normal HTTP 202 shape is generic. Throttle 429 is explicit and must remain; global readiness maps to a generic 503. Errors after readiness in issuance are logged without identifying an account in the public response. The response floor is a **minimum**, not a cap: a slow known path, lock wait, DB pool queue, event-loop pause or worker contention can exceed it. No arbitrary delay increase is recommended.

## Statistical audit and historical interpretation

The official helper calculates AUC as `P(T_known > T_unknown) + 0.5 P(tie)` over every known/unknown pair. Its binary-search tie handling and interpolated median/p95 arithmetic agree with deterministic fixtures: identical arrays give AUC .5, known always larger gives 1, and known always smaller gives 0. This establishes the elementary ranking calculation, not bootstrap calibration under workload dependence. AUC below .5 indicates known requests rank *faster*; an attacker can invert that direction. AUC is a ranking probability, not directly a per-address attack success probability under a constrained probing budget.

The test uses a fixed LCG seed, 50 complementary order pairs shuffled into 100 blocks of eight, each block four known and four unknown, and two `Promise.all` waves of four. Each of the eight slots has 50 known requests. It resamples 100 entire blocks with replacement 10,000 times and takes percentile 2.5/97.5 intervals. It pools cross-slot and cross-block pairs for AUC; no slot-stratified estimate is used. The block bootstrap preserves within-block wave/slot dependence, but not dependence across blocks, drift across conditions, or DB/worker queue state spanning blocks. Its 100 resampling units are not 800 independent latency observations. Fixed bootstrap seeds make results reproducible for a fixed trace, but do not remove sampling or environmental uncertainty. `process.hrtime.bigint` brackets the Supertest call, so the observation includes test client/Nest/HTTP overhead; `performance.now` around `auth.requestOtp` is internal service timing, with different boundaries and instrumentation overhead. Timer granularity is finer than observed millisecond jitter; actual clock calibration and network measurement error were not measured.

**Concrete protocol mismatch:** all three named conditions run exactly the same two waves of four HTTP requests per block. `healthy` and `concurrency_four` do not implement distinct HTTP concurrency levels. `slow_reject` changes the simulated worker outcome and adds 20 ms there; it also uses four-wide HTTP waves. This is established by the test loop, not a hypothesis. The test sets Express trust proxy to loopback and supplies a different synthetic `X-Forwarded-For` IP for each block. Eight requests per IP stay below the 10/minute OTP limit, so the test does **not** measure a single-IP attacker at its enforced rate limit. Known addresses are unique across conditions and mostly first issuance, while a repeated-candidate attacker may encounter the one-minute suppression path. Service timing labels are collected in completion order and assigned synthetic block numbers from that order; the published internal service medians are still descriptive, but the `serviceMs.block` field is not a reliable request-block pairing. No DB pool-wait or event-loop-delay trace was captured. Root causes such as cross-block autocorrelation, pool contention and worker interference remain **NOT ESTABLISHED**.

The sanitized JSON independently confirms every cited failure: original full `slow_reject` [.44069,.50475] and `concurrency_four` [.44936,.50342]; focused `healthy` [.44698,.50045]; later full `concurrency_four` [.43669,.50103]. Each lower endpoint falls below .45. All nine conditions have 400/400 samples, 50 known per slot, generic response shape, and median/p95 intervals inside the current limits. Seven of nine AUC points are below .5 and the published HTTP median differences are nonpositive (one rounded to zero), generally only 0–0.21 ms; this is a weak directional pattern that merits controlled study, not a demonstrated cause or deployable attack. Two concurrency median intervals exclude zero on the negative side; one later healthy p95 interval excludes zero on the positive side. Those are unadjusted exploratory observations among nine conditions and multiple metrics. Do not say there is no detectable difference in *any* metric.

An AUC point near .5 can fail because the contract requires the **whole 95% confidence interval** to lie within [.45,.55]. A lower endpoint of .43669 means the data and interval procedure have not excluded effects outside the accepted band; it is **not** proof that true AUC is below .45. All four failed AUC intervals include .5, so these intervals also do not reject the conventional point null AUC=.5. Equivalence and difference detection ask different questions; neither an inconclusive equivalence test nor non-rejection of equality proves safety. The observed interval widths .0535–.0669 are narrower than the simple i.i.d. continuous-null 95% width about .0801 for 400/400, plausible with paired block structure/common scheduling noise; without raw cross-block correlation, interval coverage is **NOT ESTABLISHED**. The internal known-path median excess is 0.90–1.25 ms in these nine cells. If the response floor is exceeded, that path difference could leak into HTTP tails; the current aggregates do not count overruns or isolate their cause.
